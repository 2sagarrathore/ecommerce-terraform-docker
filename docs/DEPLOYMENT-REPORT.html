The frontend reaches each backend by container name over the private Docker bridge network, so no backend port needs to be exposed publicly. The security group permits 3001–3004 only from members of the group itself.

Dockerfile (user-service, representative of all five)

# ---- user-service ----------------------------------------------------------------
# Small, production-only image: deps installed from the lockfile, app runs as
# the unprivileged "node" user that the base image already provides.
FROM node:20-alpine

ENV NODE_ENV=production \
    PORT=3001

WORKDIR /app

# Copy manifests first so the dependency layer is cached across code changes.
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

COPY server.js ./

USER node

EXPOSE 3001

HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD wget -q -O - http://127.0.0.1:3001/health > /dev/null 2>&1 || exit 1

CMD ["node", "server.js"]

Design choices: node:20-alpine for a small image (199 MB); manifests copied before source so the dependency layer caches; npm ci against a committed lockfile for reproducibility; the container runs as the unprivileged node user; and a HEALTHCHECK lets Docker Compose gate startup ordering.

Publishing to Docker Hub

Images were built with docker buildx for linux/amd64 and linux/arm64. This matters: the build host is an Apple Silicon Mac, so a plain docker build would have produced arm64-only images that a t3.micro cannot run. The amd64 variant was verified locally before pushing (uname -m inside the container returned x86_64 and the service answered correctly).

Security group design

The four backend rules use referenced_security_group_id pointing at the group itself rather than a CIDR, so 3001–3004 are reachable only from inside the group. This is what makes the "internal communication between services" requirement real rather than nominal — section 6 shows those ports refusing connections from the internet.

User-data: Docker install and container deployment

The rendered script performs seven steps: wait for cloud-init's apt locks; install Docker Engine from Docker's official apt repository (GPG key plus signed source list); enable the service; create the shopkart-net bridge network; pull all five images; run the four backends and the frontend with --restart unless-stopped; and finally run a smoke test against every /health endpoint, writing the result to /home/ubuntu/deployment-status.txt.

run_backend() {
  local name="$1" port="$2"
  log "Starting ${name} on port ${port}..."
  docker rm -f "${name}" >/dev/null 2>&1 || true
  docker run -d \
    --name "${name}" \
    --network "${NETWORK}" \
    --restart unless-stopped \
    -e "PORT=${port}" \
    -p "${port}:${port}" \
    "${DOCKERHUB_USER}/shopkart-${name}:${IMAGE_TAG}"
}

run_backend user-service 3001
run_backend products-service 3002
run_backend orders-service 3003
run_backend cart-service 3004

# --- 6. Run the frontend --------------------------------------------------
# Published on both the configured host port (80 by default) and 3000, and
# pointed at the backends by their container names on the Docker network.
log "Starting frontend..."
docker rm -f frontend >/dev/null 2>&1 || true

# Always publish 3000; add the configured host port too when it differs.
PORT_ARGS=(-p "3000:3000")
if [ "${FRONTEND_HOST_PORT}" != "3000" ]; then
  PORT_ARGS+=(-p "${FRONTEND_HOST_PORT}:3000")
fi

docker run -d \
  --name frontend \
  --network "${NETWORK}" \
  --restart unless-stopped \
  -e "PORT=3000" \
  -e "USER_SERVICE_URL=http://user-service:3001" \
  -e "PRODUCTS_SERVICE_URL=http://products-service:3002" \
  -e "ORDERS_SERVICE_URL=http://orders-service:3003" \
  -e "CART_SERVICE_URL=http://cart-service:3004" \
  "${PORT_ARGS[@]}" \
  "${DOCKERHUB_USER}/shopkart-frontend:${IMAGE_TAG}"

7. Security notes

  • Backend ports 3001–3004 accept traffic only from the security group itself; verified externally as refused.
  • No SSH ingress rule is created unless allowed_ssh_cidr is set explicitly; this deployment ran with no SSH exposure at all.
  • IMDSv2 is required on the instance and the root EBS volume is encrypted.
  • Containers run as a non-root user with --restart unless-stopped.
  • allowed_http_cidr was narrowed from 0.0.0.0/0 to a single /32 after the public-access evidence above was captured, so the frontend was not left open to the internet.
  • The Docker Hub token path is optional and unused here: the images are public, which keeps credentials out of user-data (readable through the metadata service).

8. Teardown

Every resource lives inside the dedicated VPC, so a single command removes all 14 and leaves nothing behind:
